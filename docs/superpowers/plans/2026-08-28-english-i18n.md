# English translation (i18n) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a full English translation of the app (web + WhatsApp bot), toggled from the header and persisted per-account, defaulting every account to Portuguese.

**Architecture:** `react-i18next` in the web app, reading/writing a new `profiles.language` column via the existing `updateProfile()`. A new `whatsapp-bot/src/locales.js` + tiny `t()` helper mirrors the same idea for the bot (separate file — the bot's Docker build context can't reach `src/` in the web app). Every hardcoded Portuguese string in `src/pages/*.jsx` and `src/components/*.jsx` gets extracted into `src/locales/{pt,en}.json` behind a `t('namespace.key')` call.

**Tech Stack:** React (Vite), `react-i18next` + `i18next` (new deps), Supabase (Postgres), plain Node/ESM (bot side, no new dep).

**Spec:** `docs/superpowers/specs/2026-08-28-english-i18n-design.md`

## Global Constraints

- No JS test framework in this repo — verification is `npm run build` (compile-time correctness) plus manual reasoning/spot-checks, matching every other feature here.
- SQL migrations are applied manually in the Supabase SQL Editor — writing/committing the `.sql` file is the deliverable; running it is a separate step, called out explicitly.
- Every account defaults to `'pt'`. No browser-locale auto-detection.
- Translation keys are namespaced `<file-basename-lowercase>.<snake_case_description>`, e.g. `comunidade.search_placeholder`. Every key added to `pt.json` must have a matching key in `en.json` in the same task/commit — never leave one language incomplete.
- `alert()`/`confirm()` strings, `placeholder=`, `title=`, and `aria-label=` attributes are in scope exactly like JSX text nodes — all are player/admin-visible copy.
- Don't touch `Comunidade.jsx`'s or `GerirClube.jsx`'s just-shipped bug fixes (Trello #133/#134/#135, commit `7f39ff4`) beyond wrapping their existing strings in `t()` — no behavior changes.

## Task 1: Database migration — `profiles.language` column

**Files:**
- Create: `supabase/migration_add_profile_language.sql`
- Modify: `supabase/schema.sql`

**Interfaces:**
- Produces: `profiles.language` (`TEXT NOT NULL DEFAULT 'pt'`, `CHECK (language IN ('pt','en'))`). Every later web task reads it via `profile.language` (from `useAuth()`) and writes it via `updateProfile({ language })`. Every later bot task reads it via each file's existing `.from('profiles').select(...)` call, adding `language` to the column list.

- [ ] **Step 1: Write the migration file**

```sql
-- ════════════════════════════════════════════════════════════════════════
-- English translation (RANKING... no, i18n v1): profiles.language, the
-- account-level UI language preference. Default 'pt' for every account,
-- new or existing — no auto-detection, matches this app's Portuguese-first
-- principle (CLAUDE.md). Set explicitly via the header toggle only.
--
-- Run this whole file in Supabase → SQL Editor → New query → Run.
-- ════════════════════════════════════════════════════════════════════════

ALTER TABLE profiles ADD COLUMN IF NOT EXISTS language TEXT NOT NULL DEFAULT 'pt';

ALTER TABLE profiles DROP CONSTRAINT IF EXISTS profiles_language_check;
ALTER TABLE profiles ADD CONSTRAINT profiles_language_check CHECK (language IN ('pt', 'en'));

COMMENT ON COLUMN profiles.language IS 'UI language preference (pt/en). Client-writable via updateProfile — not security-sensitive like rating, no column-grant protection needed.';
```

- [ ] **Step 2: Add the same column to `schema.sql`, for fresh installs**

In `supabase/schema.sql`, find the `profiles` table definition (`CREATE TABLE profiles (...)`) and add a `language` column matching Step 1's default/check, next to the other simple user-settings columns (e.g. near `preferred_side`).

- [ ] **Step 3: Commit**

```bash
git add supabase/migration_add_profile_language.sql supabase/schema.sql
git commit -m "feat(i18n): add profiles.language column (migration not yet run)"
```

Note in the commit message (and to the user) that this migration needs to be run manually in Supabase SQL Editor before `language` exists as a real column — same as every other migration in this repo.

## Task 3: `formatDate` helper

**Files:**
- Create: `src/lib/formatDate.js`

**Interfaces:**
- Produces: `formatDate(dateInput, lang, options?)` — `lang` is `'pt'` or `'en'` (pass `i18n.language` from `useTranslation()`'s `i18n` object at each call site). Returns the same kind of string `date.toLocaleDateString('pt-PT', options)` already returns today, just locale-aware. Consumed by Task 13 (`PlayerDetails.jsx`) and any other task whose file calls `toLocaleDateString`/`toLocaleTimeString` — grep each file for `toLocaleDate` and `toLocaleTime` before starting its task to check whether it applies.

- [ ] **Step 1: Write the helper**

```js
// Locale-aware date/time formatting. 'en' maps to en-GB (not en-US) — same
// day/month ordering players are already used to from pt-PT, just in
// English words, rather than also flipping to month/day order.
const LOCALE_MAP = { pt: 'pt-PT', en: 'en-GB' }

export const formatDate = (date, lang, options) =>
  new Date(date).toLocaleDateString(LOCALE_MAP[lang] || 'pt-PT', options)

export const formatTime = (date, lang, options) =>
  new Date(date).toLocaleTimeString(LOCALE_MAP[lang] || 'pt-PT', options)
```

const pt = {

const en = {

  help_text: `🤖 *Bot commands*

To join a mix:
• *Alinho* / *In* / *Dentro* / *Estou dentro*

To leave a mix:
• *Out* / *Fora* / *Estou fora* / *Saio*

• *Out 1234*

If the mix is full, the bot asks if you want to join as a substitute — reply *Sim* or *Não*. When someone leaves, the first substitute joins automatically.

To see this list:
• */help*`,
}

const DICTS = { pt, en }

// {{var}} interpolation, no library — this bot's message surface is small
// enough that hand-rolling matches the web app's i18next approach in spirit
// without a new dependency in a process that already has few of them.
export function t(key, lang, vars = {}) {
  const dict = DICTS[lang] || DICTS.pt
  let str = dict[key] ?? DICTS.pt[key] ?? key
  for (const [k, v] of Object.entries(vars)) {
    str = str.replaceAll(`{{${k}}}`, v)
  }
  return str
}
